# LiDAR Performance Analysis Platform
## Formal JSON Schemas & API Contracts

**Version:** 1.0  
**Schema Standard:** JSON Schema Draft 2020-12  
**API Style:** REST / JSON  
**Units:** SI internally  
**Probability:** `[0,1]`  
**Angles:** radians internally; degrees may be used at presentation/API boundary only if explicitly documented

---

# 1. Design Principles

These schemas enforce six fundamental principles:

1. **Unknown values are represented explicitly.**
2. **Every externally sourced parameter has provenance.**
3. **Validated user values override AI extraction.**
4. **Derived/modelled/simulated values are distinguishable from source data.**
5. **Simulation results are reproducible.**
6. **A result must contain enough metadata to reconstruct the simulation that generated it.**

The data model is organized around:

```text
Sensor
   │
   ├── Provenance
   ├── DetectionModel
   └── Assumptions
          │
          ▼
Scenario
          │
          ▼
Simulation
          │
          ▼
Results
```

# 2. Common Enumerations

These enums should be implemented once and reused throughout the application.

## 2.1 Data Origin

```text
SOURCE
USER_DEFINED
DERIVED
ASSUMED
MODELED
SIMULATED
EMPIRICAL
```

Meaning:

| Origin | Meaning |
|---|---|
| SOURCE | Directly extracted from a manufacturer or authoritative source |
| USER_DEFINED | Explicitly entered by the user |
| DERIVED | Calculated from other parameters |
| ASSUMED | Engineering assumption |
| MODELED | Generated by a mathematical/physical model |
| SIMULATED | Produced by simulation |
| EMPIRICAL | Obtained from experimental measurements |

# 4. Parameter Value Schema

Most sensor parameters should not simply be stored as:

```json
"range": 70
```

Instead:

```json
{
  "value": 70,
  "unit": "m",
  "origin": "SOURCE",
  "provenance": {}
}
```

Formal schema:

```json
{
  "$id": "https://lidar-analysis.local/schema/parameter.json",

  "title": "Parameter",

  "type": "object",

  "required": [
    "value",
    "unit",
    "origin"
  ],

  "properties": {

    "value": {
      "type": ["number", "integer", "null"]
    },

    "unit": {
      "type": ["string", "null"]
    },

    "origin": {
      "type": "string",
      "enum": [
        "SOURCE",
        "USER_DEFINED",
        "DERIVED",
        "ASSUMED",
        "MODELED",
        "SIMULATED",
        "EMPIRICAL"
      ]
    },

    "status": {
      "type": "string",
      "enum": [
        "known",
        "unknown",
        "not_applicable",
        "estimated"
      ],
      "default": "known"
    },

    "definition": {
      "type": ["string", "null"]
    },

    "conditions": {
      "type": ["string", "null"]
    },

    "provenance": {
      "$ref": "provenance.json"
    }
  },

  "additionalProperties": false
}
```

# 26. Critical Business Rules

The backend must enforce the following rules independently of the frontend.

### Rule 1

`reflectivity` must be:

```text
0.1 ≤ ρ ≤ 1.0
```

for MVP.

### Rule 2

Tree DBH must be:

```text
0.05 m ≤ D ≤ 1.0 m
```

### Rule 3

Probability must always satisfy:

```text
0 ≤ P ≤ 1
```

### Rule 4

Geometric coverage must satisfy:

```text
0 ≤ C_g ≤ 1
```

### Rule 5

Monte Carlo trials:

```text
1,000 ≤ M ≤ 100,000
```

for standard Monte Carlo operation, unless an explicit engineering mode permits another value.

### Rule 6

Simulation duration must be:

```text
T > 0
```

### Rule 7

Unknown sensor parameters cannot be silently substituted.

### Rule 8

A detection model cannot use a parameter whose status is `unknown` unless that model explicitly supports an alternative.

### Rule 9

A simulation must reference an immutable sensor version.

### Rule 10

Simulation results must retain the random seed.

# 35. Important Architectural Decision

The application should treat the following as **separate concepts**:

```text
Sensor Specification
       ≠
Detection Model
       ≠
Scenario
       ≠
Simulation Configuration
       ≠
Simulation Result
```

This separation is essential.

For example, changing the detection model should not modify the underlying sensor specification.

Likewise, changing a scenario should not modify the sensor model.

---

# 36. Required Immutability Rules

After a simulation is completed:

```text
Sensor version
Scenario version
Detection model version
Simulation configuration
Random seed
Software version
Model version
```

must remain associated with the result.

If the sensor is subsequently changed, the existing result must remain unchanged.

# 40. Final Contract Principle

The system's data architecture should make it impossible—or at minimum difficult—for an AI coding agent to blur the distinction between:

```text
"What the manufacturer said"
"What the user entered"
"What we derived mathematically"
"What we assumed"
"What our model predicts"
"What the Monte Carlo simulation produced"
"What was experimentally measured"
```

That distinction is a core engineering requirement, not merely a documentation feature.

The resulting architecture is:

```text
                   ┌──────────────┐
                   │   DATASHEET  │
                   └──────┬───────┘
                          │

                   ┌──────────────┐

                          ▼

                   │    MODEL     │
                   └──────┬───────┘
                          │
              ┌───────────┴───────────┐
              ▼                       ▼
       ┌──────────────┐       ┌──────────────┐
       │   DETECTION  │       │  PROVENANCE  │
       │     MODEL    │       │  & ASSUMPTIONS│
       └──────┬───────┘       └──────────────┘
              │
              ▼
       ┌──────────────┐
       │   SCENARIO   │
```
